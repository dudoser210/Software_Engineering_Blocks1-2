# Техническое задание: UniEats

Документ использует ключевые разделы ГОСТ 19.201 и идеи ГОСТ 34.602 в сокращенном учебном виде. Это не заявление о полном соответствии стандартам.

## 1. Введение

Наименование: информационная система заказа еды **UniEats**. Система рассчитана на студентов и сотрудников университета, сотрудников кухни и администратора сервиса.

## 2. Основание для разработки

Основание — учебное задание по проектированию распределенной микросервисной системы. Заказчик и исполнитель — учебная команда из трех человек.

## 3. Назначение разработки

Система должна давать пользователю возможность просматривать меню и оформлять заказ, кухне — получать заказ асинхронно, а оператору — просматривать уведомления и сводную статистику.

Основные цели:

- продемонстрировать декомпозицию на шесть микросервисов;
- применить event-driven architecture и Kafka;
- показать осознанный выбор SQL, NoSQL и кэша;
- обеспечить единый вход с routing, load balancing и rate limiting;
- обеспечить воспроизводимый локальный запуск.

## 4. Требования к системе

### 4.1 Функциональные требования

Система должна:

1. регистрировать пользователя с уникальным email;
2. выдавать список доступных блюд;
3. кэшировать меню на 60 секунд;
4. принимать заказ и возвращать его идентификатор;
5. передавать созданный заказ кухне через Kafka;
6. формировать уведомления по событиям заказа;
7. сохранять историю событий и строить счетчики по типам;
8. предоставлять health endpoint каждого компонента.

### 4.2 Требования к данным

- PostgreSQL хранит пользователей, каталог, заказы и статусы кухни, поскольку этим данным нужны ограничения, уникальность и транзакции.
- MongoDB хранит документы уведомлений и неизменяемый архив событий: форматы событий могут различаться и развиваться.
- Valkey хранит временную копию меню; потеря кэша не приводит к потере исходных данных.
- Каждый сервис самостоятельно владеет своими данными. Общий PostgreSQL-контейнер — только локальная экономия ресурсов.

### 4.3 Требования к надежности

- consumer подтверждает offset только после успешной обработки;
- повторная обработка события не должна создавать дубликаты в кухне и архиве;
- перезапуск контейнера не должен удалять данные в Docker volumes;
- недоступность notification/analytics не должна блокировать создание заказа;
- сервисы повторяют подключение к инфраструктуре при старте.

### 4.4 Требования к безопасности

- внешний доступ идет через Gateway;
- Gateway ограничивает поток до 10 запросов/сек на IP с burst 20;
- секреты задаются через `.env`, файл исключен из Git;
- для production необходимы TLS, JWT/OIDC, Kafka ACL и отдельные учетные записи БД; в учебный MVP они не входят.

### 4.5 Требования к программным средствам

Windows 10/11, WSL 2, Docker Desktop, Docker Compose v2, Git. Для работы приложения не требуется локально устанавливать Python, PostgreSQL, Kafka или MongoDB.

## 6. Порядок контроля и приемки

Система считается принятой при выполнении следующих условий:

1. `docker compose up --build -d` завершается без остановившихся контейнеров;
2. `GET /health` возвращает HTTP 200;
3. каталог возвращает три тестовые позиции, повторный запрос имеет `X-Cache: HIT`;
4. создание заказа возвращает HTTP 202 и `order_id`;
5. через не более 10 секунд заказ виден кухне, а события — в уведомлениях и аналитике;
6. Kafka UI показывает topics `order.created` и `kitchen.order.accepted`;
7. частые запросы приводят к HTTP 429, демонстрируя rate limiting.

## 7. Границы MVP

В состав MVP не входят реальная оплата, отправка SMS/email, web-интерфейс, production-аутентификация, кластер Kafka из трех brokers, Kubernetes и автоматическое резервное копирование. Эти функции отмечаются как развитие, а не выдаются за реализованные.
