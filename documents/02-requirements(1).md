# User Stories, Use Cases и NFR

## User Stories

**US-01.** Как студент, я хочу зарегистрироваться, чтобы система могла связать заказ со мной.

Критерии приемки: корректные данные создают пользователя; повторный email дает 409; ответ содержит `user_id`.

**US-02.** Как студент, я хочу быстро увидеть меню, чтобы выбрать блюдо без долгого ожидания.

Критерии приемки: показываются только данные каталога; второй запрос обслуживается кэшем; кэш обновляется не позднее чем через 60 секунд.

**US-03.** Как студент, я хочу отправить заказ и сразу получить подтверждение приема, чтобы не ждать работу кухни.

Критерии приемки: API отвечает 202; заказ записан в PostgreSQL; событие `OrderCreated` опубликовано в Kafka.

**US-04.** Как сотрудник кухни, я хочу автоматически получать новые заказы, чтобы начать приготовление.

Критерии приемки: consumer читает `order.created`; повторное событие не создает второй заказ; публикуется `KitchenOrderAccepted`.

**US-05.** Как студент, я хочу получать изменения статуса, чтобы понимать состояние заказа.

Критерии приемки: notification-service получает оба вида событий и сохраняет понятное уведомление.

**US-06.** Как аналитик, я хочу видеть число событий каждого типа, чтобы оценить прохождение заказов по воронке.

Критерии приемки: события сохраняются в MongoDB; `/stats` возвращает агрегированные счетчики.

## Use Case UC-01: создать заказ

**Актор:** студент.  
**Предусловия:** система запущена; пользователь зарегистрирован; позиция меню известна.  
**Триггер:** студент подтверждает заказ.

Основной поток:

1. Клиент выполняет запрос `POST /api/orders/orders`.
2. Gateway проверяет лимит и выбирает экземпляр Order Service.
3. Order Service проверяет поля запроса.
4. Order Service сохраняет заказ со статусом `CREATED`.
5. Order Service публикует `OrderCreated`.
6. Клиент получает HTTP 202 с `order_id`.
7. Kitchen Service получает событие и записывает `ACCEPTED`.
8. Kitchen Service публикует `KitchenOrderAccepted`.
9. Notification и Analytics независимо обрабатывают события.

Альтернативные варианты:

- 3a. Невалидное количество/сумма: HTTP 422, заказ не создается.
- 4a. PostgreSQL недоступен: HTTP 500; событие не публикуется.
- 5a. Kafka временно недоступна: запрос завершается ошибкой; production-решение — transactional outbox.
- 7a. Consumer недоступен: Kafka сохраняет сообщение; consumer продолжает с последнего offset после запуска.

**Постусловия:** заказ и его события доступны для аудита.

## Use Case UC-02: получить меню

**Актор:** студент.  
**Предусловия:** Catalog Service доступен.

1. Клиент выполняет запрос `GET /api/catalog/items`.
2. Catalog Service ищет ключ `catalog:items` в Valkey.
3. При cache hit сервис сразу отдает JSON и заголовок `X-Cache: HIT`.
4. При cache miss сервис получает данные из PostgreSQL, кладет результат в Valkey на 60 секунд и возвращает `X-Cache: MISS`.

**Постусловие:** исходные данные остаются в PostgreSQL; Valkey содержит временную копию.

## Use Case UC-03: просмотреть аналитику

**Актор:** оператор/преподаватель.

1. Актор вызывает `GET /api/analytics/stats`.
2. Analytics Service группирует документы MongoDB по `event_type`.
3. Сервис отправляет количество событий каждого типа.

## NFR — нефункциональные требования

| ID | Требование | Проверка |
|---|---|---|
| NFR-01 | 95% чтений каталога из кэша — до 200 мс на локальном стенде | 20 последовательных запросов |
| NFR-02 | API заказа подтверждает прием до 1 с при исправной локальной инфраструктуре | PowerShell `Measure-Command` |
| NFR-03 | Событие доходит до consumers не позднее 10 с | demo-скрипт и Kafka UI |
| NFR-04 | Не менее 100 событий сохраняются без потери при перезапуске consumer | остановка consumer, отправка, запуск |
| NFR-05 | Повтор события не создает дубликат кухонного заказа/архива | повторная публикация с теми же ID |
| NFR-06 | Gateway отклоняет превышение лимита с HTTP 429 | серия параллельных запросов |
| NFR-07 | Все компоненты запускаются одной командой | чистый запуск Compose |
| NFR-08 | Основные решения и код понятны студенту | комментарии + defense guide |
| NFR-09 | Потеря Valkey не приводит к потере бизнес-данных | удалить cache volume, запросить меню |
| NFR-10 | Пароли не находятся в Git | `.env` в `.gitignore`, пример без production-secret |
